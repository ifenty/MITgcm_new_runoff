# System setup: continue this project on another computer

Everything the project needs is either in git (the repositories below) or on the host (conda env, container
engine, credentials). This file is the checklist for the host part. Paths use `~/CProjects`; the original
machine used `/home/ifenty/CProjects`. If your home or user name differs, read section 6 first.

## 0. What travels and what does not

| Item | Travels through git? | On a new machine |
|---|---|---|
| Project records, `tools/esx`, tests, docs, `esx/`, `ESX-team-local/` | yes (`origin main`) | clone |
| MITgcm code (`pkg/rnf`, exf changes, verification inputs) | yes (fork `ifenty/MITgcm`, branch `new_runoff`) | clone inside the project |
| ESX-Team kit (framework master, used for upgrades) | yes (`ifenty/ESX-Team`, branch `esx-team-fixes`) | clone beside the project |
| Verification harness scripts | yes (`ifenty/MITgcm_verification_docker`) | clone beside the project, run `setup_links.sh` |
| Conda env `mitgcm_rnf`, container image `mitgcm:latest`, docker shim, podman config | no | rebuild (sections 3 and 4) |
| `devel-loop/loop_state/` (active issue, review packets, **verification evidence**, accounting) | **no** (gitignored) | not portable; see section 8 |
| `.claude/settings.local.json` (permissions), `.claude/esx-loop*` | no | recreate (section 7) |
| Claude auto-memory (`~/.claude/projects/.../memory/`) | no | optional copy (section 7) |
| Build and run output (`MITgcm/verification/*/build_esx*`, `output_esx_*`) | no | regenerated by the oracle script |

## 1. Prerequisites

- Linux x86_64 (the image uses gfortran, optfile `linux_amd64_gfortran`), git, an SSH key registered with GitHub
  (remotes use `git@github.com:`; the harness repo uses https), podman or Docker, about 20 GB free disk, 8+ cores
  (the full 72-command suite takes about 2 hours on the original 64-core host under light load; the standard suite takes minutes).
- Miniforge/conda (conda-forge channel).
- Claude Code CLI, logged in. Hooks use the system `python3` (stdlib only, 3.11+).
- `git config --global user.name` and `user.email` set (the original used `ifenty`).

## 2. Clone the repositories (sibling layout is required)

```bash
mkdir -p ~/CProjects && cd ~/CProjects
git clone git@github.com:ifenty/MITgcm_new_runoff.git
git clone https://github.com/ifenty/MITgcm_verification_docker
git clone git@github.com:ifenty/ESX-Team.git && git -C ESX-Team checkout esx-team-fixes
cd MITgcm_new_runoff
git clone -b new_runoff git@github.com:ifenty/MITgcm.git MITgcm        # ignored by the project repo
git -C MITgcm remote add upstream https://github.com/MITgcm/MITgcm.git
```

Rules that still hold: commit and push MITgcm code to the fork's `new_runoff` only; never push to `upstream` or the
fork's `master`; the project repo pushes to `origin main`; the harness repo is a protected repository (do not edit it).

## 3. Conda environment (the one interpreter for every ESX and test command)

```bash
conda create -n mitgcm_rnf -c conda-forge python=3.14 numpy=2.4 scipy netcdf4 cftime pyyaml pytest xarray matplotlib
```

Reference versions on the original machine: python 3.14.7, numpy 2.4.6, netCDF4 1.7.4, xarray 2026.7.0,
pytest 9.1.1, PyYAML 6.0.3, scipy 1.17.1. Seals taken under a different Python minor version change the
`doc_inventory.python_units` digests, so keep 3.14 to avoid spurious stale-evidence reports.

## 4. Container engine and image

The harness calls bare `docker`. On the original host that is a podman shim; with real Docker none of the
shim steps are needed (skip to "Link the harness scripts").

Rootless podman, once per machine. The shim and the podman config exist only in the original user's home
(`~/.local/bin/docker`, 88 lines, and `~/.config/containers/containers.conf`); they are not in git. Copy them from
the original machine (`scp old:~/.local/bin/docker ~/.local/bin/docker`, same for `containers.conf`), or recreate:

1. A subuid/subgid range for your user, then `podman system migrate`:
   `echo "$USER:500000:65536" | sudo tee -a /etc/subuid /etc/subgid`
2. `~/.config/containers/containers.conf` containing
   ```
   [engine]
   cgroup_manager = "cgroupfs"
   events_logger = "file"
   ```
   (needed when the user has no systemd cgroup delegation; skip if `podman info` works without it).
3. `~/.local/bin/docker`, an executable shell script that execs `/usr/bin/podman` and, for `run`, injects
   `--security-opt label=disable` (SELinux enforcing hosts) and `--userns=keep-id:uid=1000,gid=1000` for
   `mitgcm:latest` (it runs as uid 1000; keep-id makes build and output files come out owned by you). A caller
   that passes its own `--userns/--uidmap/--gidmap/--user` gets no mapping injected. The reasoning for every
   flag is in `docs/code_map.md` ("Container engine"). `~/.local/bin` must precede `/usr/bin` on PATH.
4. For long detached runs (tmux): `loginctl enable-linger $USER`, otherwise systemd removes `/run/user/<uid>`
   when the last login closes and kills rootless podman's state.

Link the harness scripts and build the image:
```bash
cd ~/CProjects/MITgcm_new_runoff
~/CProjects/MITgcm_verification_docker/scripts/setup_links.sh "$PWD/MITgcm/verification" linux_amd64_gfortran
MITgcm/verification/docker_build.sh        # builds mitgcm:latest (podman tags it localhost/mitgcm:latest)
```
`setup_links.sh` creates absolute symlinks, untracked in the fork and listed in `MITgcm/.git/info/exclude`;
rerun it if either repo moves.

## 5. Smoke test (do this before anything else)

```bash
cd ~/CProjects/MITgcm_new_runoff
PY=~/miniforge3/envs/mitgcm_rnf/bin/python        # adjust to your conda prefix
$PY -m pytest -q tests/esx                         # framework tests: 60 pass
$PY tools/esx/loop_gate.py --doctor                # framework health
tests/mitgcm_oracle.sh lab_sea input.rnof_sp_1     # check experiment/input names in docs/verification_matrix.md first
```
The oracle script compiles, runs and compares one verification experiment in the container. A normal-end run
plus a PASS from the compare step proves the whole chain (image, shim, mounts, harness links).

## 6. Absolute paths to fix if your account or home differs

- `esx/project.json` key `"python"` pins `/home/ifenty/miniforge3/envs/mitgcm_rnf/bin/python`. Either keep that
  path valid (symlink it) or change the key to your interpreter. Editing project config changes the verification
  signature, so evidence from the other machine is stale anyway (section 8). Say in the commit that it is a
  machine-specific change.
- `docs/code_map.md` and `esx/project_profile.md` quote the original path in examples; text only.
- `tests/esx/test_framework_fixes.py` lists optional interpreters (`.../envs/ecco/bin/python`,
  `.../miniforge3/bin/python3`); missing ones are skipped.
- The harness symlinks (section 4) must be recreated on each machine, never copied.
- `.claude/settings.json` hooks use `$CLAUDE_PROJECT_DIR`, so they do not depend on the location.

## 7. Claude Code state

1. `cd ~/CProjects/MITgcm_new_runoff && claude`. The SessionStart hook says which files to read first
   (`CLAUDE.md`, `.claude/ESX-team/ARCHITECT.md`, `esx/project_profile.md`). Add `~/CProjects/ESX-Team` as an
   additional working directory (`/add-dir`) if you will work on the kit.
2. Permissions: `.claude/settings.local.json` is gitignored. Copy it from the old machine and review it (it holds
   absolute paths). Without allow rules the auto-mode classifier blocks writes to gate-checked records and to
   `.claude/` itself; add Bash/Edit rules for the tools you need rather than working around a block.
3. Auto-memory (optional): copy `~/.claude/projects/-home-<user>-CProjects-MITgcm-new-runoff/memory/` to the
   same relative place on the new machine (the directory name encodes the project path, so it must match the new
   path). It holds hand-off notes only; durable facts are in `current_status.md`, `open_issues.md` and
   `esx/project_profile.md`.
4. Notifications: `communication.provider` is `disabled` in `esx/project.json`; nothing to configure.

## 8. Continuing work, and why loop state does not move

`devel-loop/loop_state/` is local by design: it holds the active iteration, review packets, agent transcripts and
final-verification evidence, and the evidence is bound to the machine's toolchain and source signature. So:

- Hand off **between iterations**. On the old machine finish the active issue (or `loop_control.py cancel`
  and let it finish), commit the records (`closed_issues.md`, `open_issues.md`, retrospectives) and push `origin main`
  and the fork's `new_runoff`. Confirm with `git status` and `git log origin/<branch>..` in both repos.
- On the new machine: `git pull` in all three repos, run section 5, then `/esx-loop` (or
  `python3 tools/esx/loop_control.py run`). The scientific evidence must be retaken there. Every issue closes
  against the **standard** suite (`verification.scientific_groups`, 12 commands, about 6 minutes warm, 15 at most),
  run by `final_verification.py run`. The **full** 72-command suite (`verification.full`, hours) is reserved for
  special occasions: `verify.py --suite full --owner <id>`. See `esx/project_profile.md` for when.
- Do not run the loop on two machines against the same remote branches at once.
- An iteration abandoned midway cannot be resumed elsewhere: its review packets and evidence are not in git.
  Reopen the issue and start it again.

## 8b. Resource limits and the PATH fingerprint

On a shared machine the owner may cap Claude's load (the 2026-10-17 rule was 4 CPUs and 4 GB). Host commands are pinned with
`taskset -c 0-3`. Containers need `--cpus` and `--memory` on `docker run`; the harness scripts are protected, so a small
`docker` wrapper that adds those flags to `run` (`~/.local/bin/claude-capped/docker`, put first on `PATH`) does it.

`PATH` is one of the `environment_variables` in `esx/project.json`, so it is part of every verification fingerprint. Evidence taken
under one `PATH` is "stale" under another. Run **every** gate, `verify.py` and `final_verification.py` command of one iteration with
the same `PATH`, and expect retained agents (whose shells do not inherit it) to produce evidence under the plain one.
If the two have to meet, take the evidence that must match (`--check-done`, `--closeout-doctor`, `rebind-receipt`) under the
`PATH` the final suite was taken with.
