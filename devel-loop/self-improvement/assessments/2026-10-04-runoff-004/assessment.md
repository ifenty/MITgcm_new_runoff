# Assessment: doc_contract digests ast.dump output (RUNOFF-004, 2026-10-04)

- **What happened:** Bob sealed the RUNOFF-004 documentation report under the project env interpreter (Python 3.10.19). Both independent reviewers then checked it. Richard B ran the env interpreter, got `valid: true`, and confirmed the report. Richard A ran the system `python3` (3.13.12), got `documentation report is stale; regenerate the change inventory`, and raised it as a must-fix closure blocker. Both reviewers' must-fix lists opened with that item, on a report whose content both of them later confirmed as accurate.
- **The defect:** `doc_inventory.python_units` computes `context = digest(ast.dump(ModuleContext().visit(tree)))`. `ast.dump` is not a stable cross-version serialization, so the same unmodified tree digests differently per interpreter: `7230056ee9…` under 3.10.19 and `8086e2cb…` under 3.13.12, across all 57 inventoried `.py` files. Byte `sha256`s are identical under both, and `project.py signature` is interpreter-independent (`fba754589b…` under both, verified by review A), so only the documentation contract is affected.
- **Why it cost more than the tool's own error message suggests:** the message names the one explanation that was false. Review A did the right thing with it — eliminated every tree-side cause (all 29 sealed targets byte-identical to their recorded `file_sha256`, no inventoried file with an mtime after the seal, both trees at the implementer's state, the condition persisting after its own scratch directories were removed) — and then reported honestly that it could not root-cause the refusal. There was nothing in the tree to find. A reviewer following the message's advice would instead have asked for a re-seal and gotten a report that still failed under its own interpreter.
- **Cost:** two reviewer must-fix items, one wrong diagnosis, and one correction round that was partly spent re-sealing a report that was already valid. The re-seal was not wasted (it had to absorb the round-1 edits anyway), but it would not have been a must-fix. Roughly one reviewer-hour of the iteration, and a correction-budget slot that could have gone to substance.
- **Classification:** kit evidence-integrity defect, High. High rather than Medium because the deployment specifies two interpreters in normal use — hooks run the system `python3` while `{python}` is the project env — so the two sides of the seal/check pair are routinely different, and because the symmetric failure is silent: on a host whose Python matches the seal, a genuinely stale report passes. The 2026-10-04 machine move showed that host Python is not a constant.
- **Fix:** upstream in ESX-Team. Digest a normalized structural form rather than `ast.dump` output, and have `doc_contract.py` record the sealing interpreter version in the report so `check` can refuse under a different one with a message naming both versions instead of blaming the tree. Locally, pin the interpreter in `esx/project_profile.md` (done 2026-10-04), which is a workaround and is labelled as one.
- **Ledger:** TEAM-DOCCONTRACT-AST-DUMP-DIGEST-001.
