## Pipeline

Paths are under `MITgcm/`, the fork clone on the branch `new_runoff`. The
sparse-runoff package `rnf` reads a sparse runoff file with one constant
record, places its target cells on the tiles, checks the file and assigns the
exf `runoff` field at every step. A file with any other time sampling is
refused until the time handling exists (RUNOFF-005). The temperature, salinity
and tracer routines are called from their final hooks and do nothing yet. With
`useRNF=.FALSE.` no result changes. A row marked **Existing (stub)** names a
routine that is in place and empty, and says what it will do and which issue
adds it. A **Planned** row names something that does not exist. The package,
its routines and its hooks are specified in
[the package design](package_design.md). Resolve line numbers from live source.

## Verification routes

- **Single experiment:** `tests/mitgcm_oracle.sh <experiment> <input_dir> [-mpi N] [-j N]`
  compiles into `build_esx[_mpiN]`, runs into `output_esx_<input>[_mpiN]`, and
  compares against `results/`. It exits non-zero on build failure, abnormal run
  end or FAIL.
- **Suites** (configured in [project.json](../esx/project.json)):
  - `focused`: `pytest -q tests/runoff`, then lab_sea `input`, then
    `tests/rnf/refusal_check.py`, which runs the `pkg/rnf` refusal and control
    cases with the lab_sea binary that command built, then lab_sea
    `input.rnof_sp_const` (sparse = dense), then cs32 `input.seaice` and cs32
    `input.rnof_sp_icedyn` (sparse = dense on exch2).
  - `scientific`: adds MPI variants, the no-change experiments (among them
    `isomip` and `tutorial_advection_in_gyre`, which do not compile `rnf`; the
    second is the one that runs ptracers) and the six
    lab_sea dense runoff cases `input.rnof_{const,daily,month,month1,clim,yearly}`,
    each single-process and with `-mpi 2`, followed by
    `tests/runoff/lab_sea_runoff_timing_check.py` (and `--mpi 2`), which reads
    the run directories those commands leave behind. It runs
    `tests/rnf/refusal_check.py` after lab_sea `input` as well, and
    `tests/rnf/refusal_check.py --mpi 2` after lab_sea `input -mpi 2`. The
    sparse = dense cases are lab_sea `input.rnof_sp_const` (and `-mpi 2`) and
    cs32 `input.rnof_sp_icedyn` (and `-mpi 4`); each reference in `results/`
    is a copy of the dense reference (`output.rnof_const.txt`,
    `output.icedyn.txt`). `tests/rnf/placement_probe.py` runs after cs32
    `input.rnof_sp_icedyn -mpi 4`, with the binary that command built.
- **New reference output:** `compare_results.sh` pairs `input.<X>` with
  `results/output.<X>.txt`. For a new case, run it once single-process and copy
  `output_esx_input.<X>/output.txt` to that name.
  - Run them with `/home/ifenty/miniforge3/envs/ecco/bin/python tools/esx/verify.py --suite <name> --owner <role>`.
- **Oracles and planned cases:** [verification_matrix.md](verification_matrix.md).
- **Underlying harness scripts:** `MITgcm/verification/{experiment_compile,experiment_run_no_compile,compare_results}.sh`
  are symlinks to `../MITgcm_verification_docker/scripts`, created by that repo's
  `scripts/setup_links.sh <path>/MITgcm/verification linux_amd64_gfortran`. They
  are untracked in the fork, listed in `MITgcm/.git/info/exclude`, so a fresh
  checkout needs `setup_links.sh` run again. Only Fortran changes need a
  recompile. Input variants go in `<experiment>/input.<X>/`, layered on `input/`.
- **Container engine (host-specific, 2026-10-04):** the harness hardcodes bare
  `docker`, but this host has no Docker. `~/.local/bin/docker` is a shim that
  execs `/usr/bin/podman`, injecting two flags into `run` that are both required
  here:
  - `--security-opt label=disable` — SELinux is enforcing, and without it the
    container cannot read the bind-mounted MITgcm tree ("Permission denied").
    Preferred over a `:z` mount suffix, which would recursively relabel the whole
    checkout on the host.
  - `--userns=keep-id:uid=1000,gid=1000` — `mitgcm:latest` runs as `USER mitgcm`
    (uid 1000). Rootless podman maps the host user to container uid 0, so uid 1000
    would fall in the subuid range and could not write host-owned files. This maps
    the host user to 1000, so build and run artifacts come out owned by the
    invoking user.

  Host prerequisites, both needed once per machine: a subuid/subgid range for the
  invoking user (`ifenty:500000:65536` in `/etc/subuid` and `/etc/subgid`, then
  `podman system migrate`) — without it podman cannot even unpack a Debian base
  image, because single-uid mapping cannot `lchown` layer files to gid 42; and
  `~/.config/containers/containers.conf` setting `cgroup_manager = "cgroupfs"`
  and `events_logger = "file"`, because this user has no systemd cgroup
  delegation. Build the image with `MITgcm/verification/docker_build.sh`.

  For a long run detached in tmux, `loginctl enable-linger <user>` is also
  needed (it does not require root). Without it, systemd removes
  `/run/user/<uid>` when the last login session closes, which kills the tmux
  session and breaks rootless podman, since that runtime directory holds its
  state.

  Two differences from a real `docker build`: podman builds in OCI format, so the
  Dockerfile's `SHELL ["/bin/bash","-c"]` is ignored and `RUN` steps use
  `/bin/sh` (every `RUN` there is POSIX-compatible, so image content is
  unaffected); and the image is tagged `localhost/mitgcm:latest`, which
  short-name resolution still finds.
- **Upstream contribution checks:** full `testreport` (and `-mpi`) on master versus
  the branch, and `tools/do_tst_2+2`. See the
  [project profile](../esx/project_profile.md).
